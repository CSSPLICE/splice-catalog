## 1. Executive summary

SPLICE can improve detection of sustained session abuse and visibility into distributed campaigns. It cannot reliably classify slow or distributed automation that deliberately supplies the same observations as legitimate educators. More aggressive exclusions based on regular timing, shared resources, shared networks, or coordinated navigation would recreate known false positives.

The three strongest practical directions, ranked by usefulness with the current application and implementation cost, are:

1. **Bounded multi-window session analysis, initially in a separate shadow evaluator.** Use existing durable timestamps and identities to study sustained rates, repeated traversal and coverage over longer histories. This provides measurable evidence about longer attacks without delaying every interaction or rejecting predictable educator behavior.
2. **A bounded cross-session, cross-IP campaign observer.** Correlate item sequences and time-bucket coverage independently of network/UA equality. This can identify an aggregate anomaly; membership in that anomaly must not independently exclude an educator's events.
3. **A selectively invoked, server-verified step-up experiment, only if the first two show a useful need.** This adds evidence unavailable from ordinary click logs and can increase automation cost. It requires separate UX/accessibility/privacy and product approval; neither mandatory login nor CAPTCHA nor a commercial provider is a prerequisite for Phase 3B.

The first two are **measurement improvements, not validated new blocking rules**. The third is an optional verification architecture, not proof of humanity or an automatically authorized integration. No new automatic exclusion of sophisticated automation is justified by the present evidence alone.

## 2. Current system capabilities

### 2.1 Verified ingestion and finalization boundary

The three browser event routes are `POST /usage/entry-click`, `/usage/external-click` and `/usage/web-search`; `/usage/session` issues credentials without counting usage. [src/routes/usage.ts:8–21][routes]

The actual path is:

1. HTML responses may issue a server-generated random cookie/token pair; the shared header exposes the tracking token to the page. Session issuance is public, not an educator authentication check. [src/middleware/liveUsageProtection.ts:33–70][issue] [src/views/partials/header.ejs:1–4][header]
2. The tracker sends a fresh event ID for each trusted click/auxclick or explicit search submission. It retries credential failures and provisional 503 responses once with the same ID; it does not cancel navigation. [src/public/js/usageTracking.js:58–118][tracker]
3. The controller validates input, classifies browser credentials/behavior, and resolves canonical item snapshots for eligible clicks. Enforce mode **and** an enabled provisional service select delayed admission; off/observe or a disabled provisional service do not use that pipeline. [src/controllers/UsageController.ts:24–79][controller-stage] [src/controllers/UsageController.ts:89–109][controller-search] [src/controllers/UsageController.ts:121–218][controller-click]
4. Eligible events become `PENDING`, with a unique domain-separated HMAC event key. Credentialed withheld evidence can enter the ledger without payload; invalid-origin/invalid-credential attempts generally stop before it. [src/services/ProvisionalUsageService.ts:368–405][stage]
5. A due finalizer rechecks session evidence, optionally observes a same-network/full-UA sequence, then atomically inserts an official event and records terminal status with payload redaction. `202` and `counted:false` are not an official count; even a duplicate response reporting `ACCEPTED` adds no new official row. [src/services/ProvisionalUsageService.ts:165–267][finalize]

Official statistics continue to use `usage_events` and `search_events`; no challenge result or bot-confidence metric is part of those schemas. Public API search counting and historical Nginx processing are outside this research's proposed changes. [src/services/UsageStatisticsService.ts:95–109][official-usage] [src/services/SearchStatisticsService.ts:20–45][official-search]

**Verified temporal limits:** default review is 120 seconds, deadline 15 minutes, retention one hour; finalizer batch 100, row capacity 100,000 and each evidence query bounded at 5,001 rows. A row's default evidence horizon is **receivedAt − 60 seconds through its stored reviewAfter**, a 180-second span, not the entire retained hour. Session credentials have a fixed 30-minute lifetime. Retention is not equivalent to the evaluation window or guaranteed physical deletion time. [src/services/ProvisionalUsageService.ts:32–43][defaults] [src/services/ProvisionalUsageService.ts:188–226][evidence] [src/services/LiveUsageBotProtection.ts:54–68][thresholds]

Browser requests no longer consume the API IP budget. Existing session thresholds remain: more than 12 events in two seconds, more than 6 same-kind/identity events in ten seconds, more than 12 distinct entries in ten seconds, more than 60 events in a minute for review, and more than 240 for session-abuse rejection. These are current rules, **not proposed or changed Phase 3 thresholds**. [src/services/LiveUsageBotProtection.ts:212–261][browser-checks]

## 4. Slow bot investigation

At a 3–5-second cadence, distinct clicks are approximately 12–20 per minute, below the current session-rate threshold. Distinct resources avoid rapid repetition, and twenty events offer limited evidence of sustained activity. The existing test's acceptance follows from the policy, not a broken burst detector. [src/services/LiveUsageBotProtection.ts:238–251][browser-behavior] [tests/phase2-evaluator.test.mjs:29–32][evaluator-tests]

| Candidate signal                          | Defensible use / hypothesis                                                                               | Educator overlap and bypass                                                                                                | Recommendation                                                                                          |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Low variance or repeated timing intervals | Describe cadence or implementation regularity.                                                            | Demonstrations, repetitive review, assistive workflows and queued delivery can be regular; bots can add jitter.            | Observation only; never reject solely for regularity.                                                   |
| Longer-term rates across multiple windows | Detect sustained volume missed by a short burst window.                                                   | Course preparation may be intensive; rotating sessions or reducing rate evades it.                                         | Evaluate bounded histories in shadow mode, with matched educator controls.                              |
| Resource diversity                        | Describe breadth of discovery.                                                                            | Breadth is the catalog's intended use. A bot can repeatedly use a narrow subset.                                           | Supporting context, never a standalone reason.                                                          |
| Catalog coverage/traversal                | Repeated near-exhaustive cycles may expose a campaign.                                                    | Small result sets, audits, predictable listing order and educators reviewing a topic can look similar.                     | Measure against a fixed eligible catalog snapshot and controls; numeric ID order alone is insufficient. |
| Repeated ordered sequences or loops       | Repeated long paths may warrant investigation.                                                            | Returning to familiar resources, shared curricula and demonstrations create repeats. A bot can randomize paths.            | Record exact sequence explanation and sample size; do not infer certainty.                              |
| Session duration                          | Helps normalize observations over elapsed credential time.                                                | A tab left open is not attention; automation can wait or renew.                                                            | No long-session or short-session exclusion.                                                             |
| Entry/external balance                    | Could describe workflow if collected/joined correctly.                                                    | Some professors only discover resources; others use direct detail/external links. No external callback proves consumption. | Never require an external click or a prior entry.                                                       |
| Navigation context                        | A server-bound page issuance receipt could distinguish a blind sender from a client that fetched context. | Real browsers and HTTP bots can fetch receipts; cache/history/tabs complicate absence.                                     | Optional later protocol experiment; not an existing signal or human proof.                              |
| Resource-side outcomes                    | A confirmed integration into a course would be stronger evidence of meaningful use.                       | Catalog does not observe external tool use or course integration; requiring callbacks changes scope and semantics.         | Do not assume, collect or require it in Phase 3B.                                                       |

**Recommendation:** first compare the existing minute-scale features with bounded 5- and 15-minute **historical context** in an offline evaluator. Those are experiment windows, not new production thresholds. Keep the 120-second finalization delay and official statistics unchanged. Use earlier retained observations, not future events beyond an event's review horizon. The session index can support longer same-session lookbacks within existing retention; no new browser telemetry is needed for this prototype.

Extending the **hold before counting** to 5/15 minutes is a different choice: it delays every professor's dashboard visibility, grows pending sensitive payload storage, approaches the current 15-minute deadline, and still misses indistinguishable automation. It is not justified now. Extending context beyond an hour would require retention/capacity/privacy review; extending identity across 30-minute credential renewals would require new linkage, not a simple time-window setting.

For any pair of traces identical in credentials, item/kind sequence, server receipt times and other available evidence, the evaluator must return the same result regardless of whether a fixture labels it professor or bot. Twenty slow clicks on selected resources can satisfy this condition. No entropy feature, timing model or arbitrary score can recover a label absent from the observations.

## 5. Distributed bot investigation

Historical multi-IP GET traversal is evidence about fetching pages. It does not establish that the same actors invoke the live tracking protocol. Merely crawling HTML can produce zero live clicks; deliberately polluting live totals requires valid credentials/tokens/event IDs and supported payloads, or a real browser driving the tracker. The reviewed session endpoint allows credential acquisition without educator login. [src/middleware/liveUsageProtection.ts:62–70][issue] [src/controllers/UsageController.ts:121–158][controller-click]

| Live attack behavior                      | What SPLICE can currently see                                                                          | Limitation                                                                                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| One/two valid events per session, one IP  | Different sessionKeys and common networkKey.                                                           | Counts and fresh sessions alone do not establish shared control.                                                          |
| Session rotation across unrelated IPs     | Different session/network keys; same-kind item identities and time remain comparable.                  | Current finalizer queries other sessions only within the target networkKey **and** agentKey cohort.                       |
| UA changes between sessions               | Different agentKeys.                                                                                   | No session inconsistency; a common UA is not a safe substitute for an attacker identity.                                  |
| A repeated rare sequence across IPs       | Retained rows contain enough same-kind keyed identity/order/time data for a separate correlation pass. | No current cross-IP detector, distinct-IP count is not distinct people, and coordinated educators may have the same path. |
| Disjoint pieces of broad catalog coverage | Aggregate union/coverage may rise without a single long sequence.                                      | Attribution is weak: disjoint unrelated professors naturally contribute to aggregate coverage.                            |
| Sparse/staggered randomized activity      | A broad statistical shift might be observable with enough samples.                                     | At low volume, a script can match legitimate marginal distributions and avoid useful correlations entirely.               |

**Cross-IP correlation is feasible as analysis, not validated attribution.** The stable, domain-separated identityKey enables matching entry identities across IPs without storing raw IPs. A bounded observer could group repeated entry n-grams and time-bucket coverage before examining network/UA diversity. It should not start by linking sessions merely because their IPs or software match. Lack of a current cross-IP query is an implementation scope limit, not absence of all useful data. [src/services/ProvisionalUsageService.ts:202–218][evidence] [src/services/ProvisionalUsageService.ts:378–382][stage]

**Accuracy remains a hypothesis.** Compare repeated campaign structures against popular-item traffic, demonstrations, conferences and independent discovery. Session/IP diversity can strengthen an alert about a pattern but does not establish which individual clicks are automated. Once a bot randomizes timing, item choice and identities to match normal activity, it can be unidentifiable. Avoid global tainting, transitive session clusters and treating a high-coverage campaign alert as an exclusion list.

**Shared state/schema answer:** all instances already share committed ledger rows in MySQL. A small offline observer over a disposable copy needs no new entity or third-party service. A recurring observer needs consistent windows, bounded extraction/checkpoints and deduplicated observations; a durable campaign/observation table and a suitable global time index are likely appropriate. The existing indexes lead with session, network/agent, status/reviewAfter or purgeAfter, not a general receivedAt scan. Do not add an unbounded all-session scan to each event's locked finalizer transaction. [src/db/entities/ProvisionalUsageEvent.ts:17–42][entity]

The existing distinct-IP unit test accepts 100 low-volume clients. It is an injectable-address simulation, not a test of real distributed networks or proxy trust. [tests/live-usage-protection.test.mjs:199–205][distributed-test]

### Measurement protocol

- **Freeze ground truth:** fixture actor ID, intended class and unique intended interaction ID stay in the harness, outside detector inputs. A retry keeps the same event ID. Persist an expected ledger/official-key mapping only in disposable test output. The existing runner already maps keyed events to ledger states; extend it rather than infer counting from response codes. [tests/local-bot-simulations/phase2.mjs:70–85][sim-labels] [tests/local-bot-simulations/phase2.mjs:169–243][sim-measure]
- **Count actual writes:** snapshot official usage and WEB-search rows before/after an isolated scenario; reconcile accepted ledger officialEventId and kind/table to exactly one official write. Check `PENDING` before the horizon, terminal states afterward, duplicates separately, and no unaccounted official rows. Capture invalid/rejected attempts outside the ledger with the harness. Do not query unrelated API/historical data to label bots.
- **Report outcomes separately:** accepted automated events = unique bot-labeled interactions with official rows; terminally withheld automated events = unique bot-labeled interactions explicitly excluded by policy. Report resource failures, expiry, undelivered requests and still-pending interactions as separate missing/unresolved categories. They can undercount users but are not successful automation detection.
- **False positives and metrics:** FP = legitimate-labeled interactions excluded by a detection rule; TP = bot-labeled interactions excluded by that rule; FN = accepted bot-labeled interactions. On fully resolved classifier fixtures, precision = TP/(TP+FP), recall = TP/(TP+FN); an empty denominator is undefined. Report unresolved counts and all-cause legitimate loss separately, with per-scenario denominators. Do not inflate recall by counting network/storage outages as correct bot classifications. For observation-only prototypes, calculate **would-flag** precision/recall without changing official writes; these are not withheld-event metrics. Campaign-level alerts get separate labels/metrics.
- **Latency:** instrument monotonic receipt/staging, reviewAfter, terminal commit and first official visibility in the harness. Report admission duration, due-to-finalization lag and total visibility p50/p95/p99/max separately, with sample sizes and polling error. Use real wall time for at least a default 120-second subset; virtual-clock advancement is acceptable for logic tests only and must be labeled. Use server original event time for existing daily semantics.
- **Storage/CPU/locking:** compare baseline versus each observer on identical disposable traces. Record ledger pending/terminal counts, payload residence, table+index allocation at meaningful scales, observation-summary cardinality, RSS/heap, process CPU per event/batch, event-loop delay, SQL rows examined/query timings and transaction/lock wait/hold timings. Instrumentation is future harness work, not telemetry claimed present. Measure observer saturation/backlog and worker pass duration; a small InnoDB page allocation is not a per-event size benchmark.
- **Reasons:** retain existing initial/terminal reasons and a separate versioned shadow observation list with window/sample count. One terminal reason cannot capture every feature; do not overwrite official decisions to store experiment tags. Report unknown/missing verification outcomes and capacity truncation explicitly. Export only aggregate counts/timings/reasons; no raw cookies, tokens, IPs, full UAs or queries.

**Promotion gates:** retain every existing hard regression, zero additional exclusions in the educator controls, identical outcomes for identical counterfactual traces, bounded observer cost and tested restart/saturation behavior. Zero fixture errors is necessary but not evidence of zero field false positives. If no discriminator survives controls and hold-out tests, keep it as an observation or discard it. Do not lower thresholds just to improve a synthetic blocked-bot percentage.

The current simulator/helper guards already enforce loopback ownership, explicit disposable opt-in and random schema names, but the helper runs migrations and clears its own fixture tables. It must not be run during this research-only task. Future database tests require separately prepared disposable schemas; no run should attach to a forwarded persistent database merely because its port is local. [tests/local-bot-simulations/phase2.mjs:25–42][sim-safety] [tests/helpers/live-usage-mysql.mjs:13–59][mysql-helper]

Cross-kind resource linking or page-context receipts add fields/state not currently present. Third-party infrastructure is optional. An external verifier or edge provider adds signals unavailable from this origin, but brings availability/privacy/plan dependencies. Retroactive corrections would require a separate compensating/audit model and explicit dashboard/export semantics review; that is outside the recommended Phase 3B. ## 12. Known limitations

- The four requested Phase 2/2.1 review/design/test documents are missing from the reviewed tree; surviving docs include stale Phase 1 claims. Source and tests, not those claims, anchor this report.
- User-supplied manual outcomes are controlled simulations, including the invalid-traffic-during-valid-use case; Phase 3A did not rerun them. Only the two offline suites were executed (46 passing tests). No database, provider or network-scale effectiveness is claimed.
- There is no representative labeled educator dataset, field false-positive estimate, calibrated slow-bot cutoff or measured production query/locking capacity. Providers' algorithms/claims are not SPLICE validation data.
- Same session is not same person; different sessions/IPs need not mean different people or an attack. Fixed credential renewal and deliberately randomized bot behavior limit correlation. Fine-grained pseudonymous data is still privacy-relevant.
- A common resource hash across entry/external kinds, verified page history, active engagement, edge reputation and human verification outcomes are absent. Each addition needs explicit code/state and privacy justification.
- Current known-bot, UA-change, burst and rate policies can themselves exclude some legitimate tools or fast educators. Preserve their regressions while measuring this baseline risk; do not claim the current accepted set is verified human activity.
- Optional verification can be bypassed or exclude genuine educators, and account legitimacy is not per-event humanity. A mock verifier cannot establish real vendor accuracy.
- Later evidence cannot revise finalized events; outages, dropped keepalive requests, expired pending rows and storage limits cause missing data independently of automation.
- No research method can identify a bot from a live trace intentionally identical to a legitimate educator's trace using only that trace. This is a measurement boundary, not a threshold-tuning problem.

## 13. Final recommended Phase 3B direction

Approve **bounded, observation-only prototypes** for multi-window session patterns and cross-session campaigns, backed by the matrix in section 9 and worker/latency/resource measurements. Preserve current two-minute finalization, rapid-burst reevaluation, replay, credential checks, policy compatibility and official tables. Keep synchronized activity and shared-network evidence nonblocking; do not require navigation chains, telemetry presence or external clicks.

Require a review of held-out mixed educator/bot outcomes, operational bounds and privacy before proposing any new exclusion. If ambiguity remains, leave eligible counts unchanged and report the unresolved contamination. Only then consider a separately approved selective verification experiment, without mandatory login, blanket CAPTCHA, commercial service dependency or invasive fingerprints.

**What can we realistically improve without sacrificing legitimate professor usage?** We can detect more sustained and coordinated _patterns_, explain uncertainty, preserve educator interactions during attacks and failures, and selectively obtain independent verification evidence if its cost is justified. We cannot safely turn ordinary slow browsing or distributed low-volume clicks into confirmed bots. Phase 3B should improve evidence and observability first, with measurable controls protecting educators, and promote only independently justified rules after review.
